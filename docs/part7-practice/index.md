# Part 7. 실전 프레임워크와 타입 설계

Part 6까지 TypeScript 문법과 프로젝트 도구를 모두 갖췄습니다. 그런데 실무 코드는 순수 TypeScript만으로 이뤄지지 않습니다. 서버는 Express 위에서, 화면은 React나 Vue 위에서 돌아가고, 데이터는 axios로 주고받으며, 상태는 zustand나 Pinia에 둡니다. Part 7은 **이 프레임워크·라이브러리들과 TypeScript가 만나는 자리**를 배웁니다.

이 파트를 마치면 **Node.js·React·Vue 실무 코드에서 타입을 올바르게 쓰고, 좋은 타입 설계 원칙을 적용할 수 있게** 됩니다.

## 왜 이 파트가 필요한가

프레임워크를 쓰면 타입을 붙이는 방법이 조금씩 달라집니다.

- 라이브러리가 **타입을 직접 포함**하기도 하고(axios, zustand, Vue, Pinia), **`@types/` 패키지로 따로** 설치해야 하기도 합니다(Express, React).
- 같은 "컴포넌트의 입력"이라도 React는 **함수 매개변수**에, Vue는 **`defineProps`의 제네릭**에 타입을 붙입니다.
- 프레임워크마다 "여기에 타입을 적으면 나머지는 추론된다"는 **핵심 자리**가 있습니다. 그 자리를 알면 적는 양은 줄고 안전성은 커집니다.

프레임워크는 달라도 큰 그림은 같습니다.

| 프레임워크·도구 | 타입은 어디서 오나 | 타입을 직접 적는 핵심 자리 | 타입 검사 도구 |
|---|---|---|---|
| Express | `@types/express` | `Request`·`Response` 제네릭, 환경 변수 설정 | `tsc` |
| React | `@types/react` | props 타입, `useState` 제네릭, 이벤트 타입 | `tsc` |
| Vue | `vue` 패키지 자체 | `defineProps`·`defineEmits`, `ref` 제네릭 | `vue-tsc` |
| zustand·Pinia | 패키지 자체 | 스토어 상태·액션 타입 | 프로젝트의 검사 도구 |
| axios + zod | 패키지 자체 | 공통 응답 타입, 응답 스키마 | 프로젝트의 검사 도구 |

그리고 모든 레슨을 꿰뚫는 원칙이 하나 있습니다. **"바깥에서 들어온 값(요청 본문, 환경 변수, API 응답, 입력창, 저장소)은 검증하기 전까지 `unknown`이다."** 타입은 실행할 때 사라지므로, 믿을 수 없는 값은 경계에서 한 번 검사한 뒤에 타입을 붙입니다. 마지막 레슨에서 이 원칙을 타입 설계 방법으로 정리합니다.

## 학습 흐름

레슨은 크게 네 묶음입니다. **순서대로 보지 않아도 됩니다.** 자기 업무에 필요한 묶음부터 보세요. 다만 각 묶음 안에서는 순서를 지키는 것이 좋습니다.

1. **서버** — [01 Node.js + Express](./01-node-express): REST API에 타입을 붙이고, 요청·환경 변수를 경계에서 검증합니다.
2. **React** — [02 React 기초](./02-react-basics) → [03 React 훅](./03-react-hooks) → [05 zustand](./05-zustand): 컴포넌트·props·state에서 훅·Context, 전역 스토어까지 이어집니다.
3. **Vue** — [04 Vue 3](./04-vue): `<script setup>`, `defineProps`, Pinia를 한 레슨에 담았습니다. React 레슨을 보지 않았어도 이해할 수 있게 썼습니다.
4. **공통** — [06 API 클라이언트](./06-api-client) → [07 타입 설계](./07-type-design): 프레임워크와 상관없이 쓰는 API 호출 계층과 타입 설계 원칙입니다. **어느 길로 왔든 이 두 레슨은 꼭 보세요.**

| 업무 | 추천 순서 |
|---|---|
| 백엔드(Node.js) | 01 → 06 → 07 |
| React 프런트엔드 | 02 → 03 → 05 → 06 → 07 |
| Vue 프런트엔드 | 04 → 06 → 07 |
| 전부 | 01 → 07 순서대로 |

React와 Vue를 처음 보는 사람을 위해 각 레슨은 **프레임워크 최소 개념(컴포넌트, 상태, 렌더링)** 을 짧게 설명하고 시작합니다. 프레임워크 자체를 깊이 배우는 파트는 아니므로, 더 알고 싶은 부분은 각 프레임워크 공식 문서를 함께 보세요.

## 이 파트를 마치면 할 수 있는 것

- Express REST API의 경로 매개변수·본문·쿼리·응답에 타입을 붙이고, 에러 미들웨어와 환경 변수 검증을 갖출 수 있습니다.
- React 컴포넌트의 props·state·이벤트·훅·Context에 타입을 붙이고, 제네릭 컴포넌트를 만들 수 있습니다.
- Vue SFC에서 `defineProps`·`defineEmits`·`ref`·Pinia 스토어를 타입 안전하게 쓰고 `vue-tsc`로 검사할 수 있습니다.
- zustand 스토어를 커리 패턴·셀렉터·`persist`·슬라이스로 설계할 수 있습니다.
- axios 공통 응답·에러 타입을 설계하고 zod로 응답을 검증할 수 있습니다.
- 판별 유니온·브랜드 타입·`unknown`으로 "불가능한 상태를 표현할 수 없는" 타입을 설계할 수 있습니다.

## 막힐 때 팁

::: tip 버전부터 확인하세요
프레임워크 타입은 버전에 따라 자주 바뀝니다. 예를 들어 Express 4와 5는 async 오류 처리가 다르고, React 19는 `useRef` 인자와 폼 이벤트 타입이 바뀌었고, Vue 3.5에는 반응형 props 구조 분해가 생겼습니다. 예제와 다른 오류가 나면 먼저 `npm ls 패키지이름`으로 설치된 버전을 확인하고, 레슨 위쪽의 "이 레슨의 버전" 안내와 비교하세요.
:::

- **추론된 타입은 마우스를 올려 확인합니다.** 이벤트 타입·스토어 타입처럼 이름이 길고 복잡한 타입은 외우지 말고, 인라인으로 써 놓은 뒤 마우스를 올려 나온 이름을 복사하세요.
- **개발 서버는 타입 검사를 하지 않습니다.** Vite 개발 서버는 화면이 떠도 타입 오류가 있을 수 있습니다. `npx tsc --noEmit`(Vue는 `npx vue-tsc --noEmit`)을 수시로 실행하세요.
- **긴 오류 메시지는 마지막 줄부터 읽습니다.** 프레임워크 타입 오류는 여러 줄로 길게 나오는데, 핵심 원인은 대개 맨 아래 줄에 있습니다([에러 메시지 읽는 법](../part0-start/06-how-to-read-errors)).
- **`any`·`as`·`!`로 오류를 지우고 싶어지면 멈추세요.** 대부분 "경계에서 검증하지 않았다"거나 "상태 모양이 잘못 설계되었다"는 신호입니다. [07 타입 설계](./07-type-design)에서 고치는 방법을 찾아보세요.
