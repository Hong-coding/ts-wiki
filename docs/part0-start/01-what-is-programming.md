# 프로그래밍과 JavaScript, 그리고 TypeScript

<LessonMeta level="입문" :minutes="30" prev="없음 — 위키의 첫 레슨입니다" />

## 이번에 배울 것

- 컴퓨터, 프로그램, 프로그래밍이 각각 무엇인지 내 말로 설명할 수 있다.
- 소스 코드, 컴파일, 런타임이라는 말의 뜻을 구분할 수 있다.
- JavaScript가 웹 브라우저와 Node.js에서 실행된다는 것을 설명할 수 있다.
- TypeScript가 JavaScript의 "상위 집합"이며, 실행 전에 JavaScript로 변환된다는 것을 설명할 수 있다.
- 짧은 TypeScript 코드와 그 코드가 변환된 JavaScript 코드를 보고 차이를 찾을 수 있다.

## 먼저 알아 둘 것

- 없음. 컴퓨터를 켜고 웹 브라우저로 이 페이지를 읽을 수 있으면 충분합니다.

## 비유로 이해하기

### 컴퓨터는 "아주 빠르지만 융통성이 전혀 없는 요리사"

식당 주방에 요리사가 한 명 있다고 상상해 봅시다. 이 요리사는 이런 특징이 있습니다.

- 1초에 수십억 번 칼질을 할 만큼 **엄청나게 빠릅니다.**
- 하지만 **레시피에 적힌 것만** 합니다. "적당히 간을 맞춘다" 같은 말은 이해하지 못합니다. "소금 3그램을 넣는다"처럼 정확히 적어 줘야 합니다.
- 레시피에 "설탕"이라고 적어야 할 곳에 "설탕ㅇ"이라고 오타를 내면, 그 자리에서 멈춰 버리거나 엉뚱한 재료를 넣습니다.

컴퓨터가 바로 이 요리사입니다. 그리고 이 요리사에게 건네는 **레시피가 프로그램**이고, **레시피를 쓰는 일이 프로그래밍**입니다.

### 레시피에도 "언어"가 있다

요리사가 한국어만 읽는다면 레시피도 한국어로 써야 합니다. 컴퓨터도 마찬가지로 정해진 **프로그래밍 언어**로 쓴 레시피만 읽을 수 있습니다. JavaScript, TypeScript, Java, Python은 모두 이런 프로그래밍 언어의 이름입니다.

### TypeScript는 "검수 담당자가 붙은 레시피"

이 식당에는 레시피를 주방에 넘기기 전에 **검수 담당자**가 한 번 읽어 보는 절차가 있다고 해 봅시다. 검수 담당자는 이런 것을 잡아냅니다.

- "여기 '설탕ㅇ'이라고 쓰셨는데, '설탕' 아닌가요?"
- "이 단계에는 그릇이 있어야 하는데, 앞에서 그릇을 준비하는 단계가 없어요."
- "'온도'에는 숫자를 써야 하는데 '뜨겁게'라고 쓰셨네요."

검수가 끝나면 담당자는 레시피에서 **검수용 메모를 지우고** 깔끔한 레시피만 주방에 넘깁니다. 요리사는 메모가 있었는지조차 모릅니다.

- 요리사 = 컴퓨터(정확히는 JavaScript를 실행하는 프로그램)
- 주방에 넘어가는 깔끔한 레시피 = **JavaScript**
- 검수용 메모가 붙은 레시피 = **TypeScript**
- 검수 담당자 = **TypeScript 컴파일러(tsc)**

이 비유를 기억해 두면 이번 레슨의 나머지 내용이 훨씬 쉽게 이해됩니다.

## 개념 설명

### 1단계: 컴퓨터와 프로그램

**컴퓨터**는 계산하고, 기억하고, 결과를 보여 주는 기계입니다. 노트북, 스마트폰, 매장의 POS 단말기, 키오스크 모두 컴퓨터입니다.

**프로그램(program)**은 컴퓨터가 무엇을 할지 순서대로 적어 놓은 명령의 모음입니다. 여러분이 쓰는 카카오톡, 웹 브라우저(크롬, 엣지), 엑셀이 모두 프로그램입니다. 흔히 "앱(app)"이나 "소프트웨어(software)"라고도 부릅니다.

**프로그래밍(programming)**은 이런 프로그램을 만드는 일입니다. 같은 뜻으로 "코딩(coding)", "개발(development)"이라는 말도 씁니다.

::: info 프로그램이 하는 일은 결국 세 가지
아무리 복잡한 프로그램도 크게 보면 세 가지를 반복합니다.
1. **입력**을 받습니다. (키보드로 친 글자, 마우스 클릭, 바코드 스캔, 인터넷으로 받은 데이터)
2. **처리**합니다. (계산하고, 비교하고, 저장합니다)
3. **출력**합니다. (화면에 보여 주고, 영수증을 인쇄하고, 다른 컴퓨터로 보냅니다)

예를 들어 편의점 POS 프로그램은 바코드를 **입력**받아, 가격을 찾아 합계를 **처리**하고, 화면과 영수증에 **출력**합니다.
:::

### 2단계: 소스 코드

**소스 코드(source code)**는 사람이 프로그래밍 언어로 쓴 글입니다. 줄여서 그냥 **코드**라고 부릅니다. "소스(source)"는 "원천, 원본"이라는 뜻으로, 프로그램의 원본이라는 의미입니다.

아래는 JavaScript로 쓴 아주 짧은 소스 코드입니다. 아직 문법을 몰라도 괜찮습니다. 생김새만 보세요.

```js
// 상품 두 개의 가격을 더해서 화면에 보여 줍니다
const coffee = 4500
const cake = 6000
console.log(coffee + cake)
```

```text
10500
```

한 줄씩 읽어 보면 이렇습니다.

- 첫 줄의 `//`로 시작하는 부분은 **주석(comment)**입니다. 컴퓨터는 무시하고, 사람이 읽으라고 남기는 메모입니다.
- `const coffee = 4500`은 "`coffee`라는 이름표를 만들고 4500이라는 값을 붙여 둔다"는 뜻입니다. 이런 이름표를 **변수(variable)**라고 합니다. Part 1에서 자세히 배웁니다.
- `console.log(...)`는 "괄호 안의 값을 화면에 출력한다"는 명령입니다. 앞으로 정말 자주 보게 될 명령입니다.

소스 코드는 그냥 **글자로 된 파일**입니다. 메모장으로도 열 수 있습니다. 파일 이름 끝에 붙는 **확장자**로 어떤 언어인지 구분합니다.

| 확장자 | 언어 |
|---|---|
| `.js` | JavaScript |
| `.ts` | TypeScript |
| `.java` | Java |
| `.py` | Python |

### 3단계: 컴퓨터는 소스 코드를 바로 이해하지 못한다

여기서 중요한 사실이 하나 있습니다. 컴퓨터의 두뇌인 **CPU(중앙 처리 장치)**는 사실 `console.log` 같은 영어 단어를 전혀 모릅니다. CPU가 이해하는 것은 0과 1로 이루어진 **기계어(machine code)**뿐입니다.

그래서 사람이 쓴 소스 코드를 컴퓨터가 이해하는 형태로 바꿔 주는 과정이 반드시 필요합니다. 이 "바꿔 주는" 방식에는 크게 두 가지가 있습니다.

#### 방식 1: 컴파일 — 미리 통째로 번역해 두기

**컴파일(compile)**은 소스 코드 전체를 실행하기 **전에** 다른 형태로 한꺼번에 번역해 두는 것입니다. 이 번역을 해 주는 프로그램을 **컴파일러(compiler)**라고 합니다.

비유하면, 외국 소설을 출판하기 전에 번역가가 책 한 권을 통째로 번역해 두는 것과 같습니다. 번역하는 도중에 "이 문장은 문법이 이상한데요?" 하고 문제를 미리 발견할 수 있다는 장점이 있습니다.

#### 방식 2: 인터프리트 — 실행하면서 그때그때 읽기

**인터프리트(interpret)**는 소스 코드를 한 줄씩(혹은 조금씩) 읽으면서 바로바로 실행하는 방식입니다. 이 일을 하는 프로그램을 **인터프리터(interpreter)**라고 합니다.

비유하면, 동시통역사가 연설을 들으면서 실시간으로 통역하는 것과 같습니다. 준비 없이 바로 시작할 수 있지만, 연설 중간에 이상한 문장이 나오면 **그 순간이 되어서야** 문제를 알게 됩니다.

::: info 실제로는 섞어서 씁니다
요즘의 JavaScript 엔진은 두 방식을 섞어서 씁니다. 처음에는 바로 읽어 실행하다가, 자주 실행되는 부분은 내부에서 기계어로 번역해 빠르게 만듭니다(이를 JIT 컴파일이라고 합니다). 입문 단계에서는 "JavaScript는 따로 번역 단계 없이 바로 실행할 수 있다" 정도로만 이해하면 충분합니다.
:::

### 4단계: 런타임 — 프로그램이 실제로 돌아가는 시간과 장소

**런타임(runtime)**이라는 말은 두 가지 뜻으로 쓰입니다. 둘 다 자주 나오니 구분해 두세요.

1. **실행되는 시간**: 프로그램이 실제로 돌아가고 있는 "때"를 말합니다. 반대말은 **컴파일 타임(compile time)**, 즉 실행하기 전에 번역하는 "때"입니다.
   - "이 에러는 런타임에 발생한다" = 프로그램을 실제로 실행해 봐야 터지는 에러라는 뜻입니다.
   - "이 에러는 컴파일 타임에 잡힌다" = 실행하기 전, 번역 단계에서 미리 알 수 있다는 뜻입니다.
2. **실행 환경**: 프로그램을 실제로 돌려 주는 "장소(프로그램)"를 말합니다. "JavaScript 런타임"이라고 하면 JavaScript 코드를 실행해 주는 프로그램을 가리킵니다.

TypeScript의 가장 큰 가치는 **런타임에 터질 에러를 컴파일 타임으로 끌어오는 것**입니다. 이 말은 다음 레슨에서 실제 예제로 확인합니다.

### 5단계: JavaScript는 어디서 실행되나요?

JavaScript는 원래 **웹 페이지를 움직이게 하려고** 만들어진 언어입니다(1995년). 지금도 여러분이 보는 거의 모든 웹사이트에서 JavaScript가 돌아가고 있습니다. 버튼을 누르면 메뉴가 펼쳐지고, 장바구니 숫자가 바뀌는 것이 대부분 JavaScript 덕분입니다.

JavaScript를 실행해 주는 런타임은 대표적으로 두 가지입니다.

#### 웹 브라우저

크롬, 엣지, 사파리, 파이어폭스 같은 **웹 브라우저** 안에는 JavaScript 엔진이 들어 있습니다. 예를 들어 크롬과 엣지에는 **V8**이라는 엔진이 들어 있습니다. 웹 페이지에 포함된 JavaScript 코드를 이 엔진이 읽어서 실행합니다.

::: tip 지금 바로 해 볼 수 있습니다
크롬이나 엣지에서 키보드의 `F12` 키를 누르면 오른쪽(또는 아래쪽)에 **개발자 도구** 창이 열립니다. 위쪽 탭 중 **Console(콘솔)**을 누르면 `>` 표시 옆에 글자를 입력할 수 있는 줄이 나타납니다. 여기에 `4500 + 6000`을 입력하고 `Enter`를 누르면 바로 아래에 `10500`이 나타납니다. 방금 여러분은 웹 브라우저라는 런타임에서 JavaScript를 실행한 것입니다. 다 보았으면 `F12`를 한 번 더 눌러 창을 닫습니다.
:::

#### Node.js

2009년에 **Node.js(노드 제이에스)**가 등장했습니다. Node.js는 크롬의 V8 엔진을 꺼내서 **웹 브라우저 밖에서도** JavaScript를 실행할 수 있게 만든 프로그램입니다.

Node.js 덕분에 JavaScript로 이런 것들을 만들 수 있게 되었습니다.

- 웹사이트 뒤에서 데이터를 처리하는 **서버** 프로그램
- 터미널(검은 화면)에서 돌아가는 **명령줄 도구**
- 파일을 읽고 쓰는 **자동화 스크립트**
- 그리고 이 위키에서 쓸 **TypeScript 컴파일러** 자체도 Node.js 위에서 돌아갑니다.

| 구분 | 웹 브라우저 | Node.js |
|---|---|---|
| 주로 하는 일 | 웹 화면을 움직이기 | 서버, 도구, 자동화 |
| 할 수 있는 것 | 화면의 버튼·글자 바꾸기 | 내 PC의 파일 읽고 쓰기, 서버 띄우기 |
| 할 수 없는 것 | 내 PC 파일 마음대로 읽기(보안상 막힘) | 웹 페이지 화면 조작(화면이 없음) |
| 설치 | 이미 깔려 있음 | 따로 설치해야 함 (3번 레슨) |

같은 JavaScript라도 **어느 런타임에서 실행하느냐에 따라 쓸 수 있는 기능이 다릅니다.** 이것도 나중에 꼭 다시 만나게 될 중요한 사실입니다.

### 6단계: TypeScript는 JavaScript의 상위 집합

**TypeScript**는 Microsoft가 만들어 2012년에 공개한 언어입니다. 한 문장으로 요약하면 이렇습니다.

> TypeScript = JavaScript + **타입(type)**

**타입**이란 "이 값이 어떤 종류의 값인가"를 나타내는 꼬리표입니다. 4500은 숫자(number), `'아메리카노'`는 문자열(string, 글자들의 줄)입니다. TypeScript에서는 값에 이런 꼬리표를 붙여 둘 수 있고, 컴파일러가 꼬리표대로 쓰였는지 검사합니다.

"**상위 집합(superset)**"이라는 말은 이런 뜻입니다.

- 올바른 JavaScript 코드는 (거의) 그대로 TypeScript 코드이기도 합니다.
- TypeScript는 그 위에 타입을 적는 문법을 **추가**한 것입니다.

그림으로 그리면 큰 원(TypeScript) 안에 작은 원(JavaScript)이 통째로 들어 있는 모양입니다. 그래서 JavaScript를 먼저 따로 배우지 않고, TypeScript로 바로 시작해도 JavaScript를 함께 배우게 됩니다. 이 위키의 Part 1 제목이 "TypeScript로 배우는 JavaScript"인 이유입니다.

::: info "거의"라고 쓴 이유
JavaScript로는 실행되는 코드라도, TypeScript 컴파일러가 "이건 위험해 보입니다" 하고 에러를 표시하는 경우가 있습니다. 문법이 틀려서가 아니라 **타입 검사**에 걸리기 때문입니다. 이것이 바로 TypeScript를 쓰는 이유이기도 합니다.
:::

### 7단계: TypeScript는 실행 전에 JavaScript로 변환된다

웹 브라우저도, Node.js도 기본적으로는 **JavaScript만** 실행합니다. 그래서 TypeScript 코드는 실행하기 전에 JavaScript로 바꾸는 단계를 거칩니다. 이 일을 하는 것이 **TypeScript 컴파일러**이고, 명령 이름은 `tsc`(TypeScript Compiler의 줄임말)입니다.

아래는 TypeScript 소스 코드입니다.

```ts
// 매장 이름과 오늘 주문 수
const storeName: string = '한빛 카페 강남점'
const orderCount: number = 128

console.log(storeName + ' 오늘 주문 수: ' + orderCount)
```

```text
한빛 카페 강남점 오늘 주문 수: 128
```

`: string`, `: number` 부분이 바로 **타입 표기**입니다. "`storeName`에는 문자열만, `orderCount`에는 숫자만 담겠다"는 약속입니다.

이 코드를 `tsc`로 변환하면 다음과 같은 JavaScript가 만들어집니다.

```js
// 매장 이름과 오늘 주문 수
const storeName = '한빛 카페 강남점';
const orderCount = 128;
console.log(storeName + ' 오늘 주문 수: ' + orderCount);
```

비교해 보면 다음과 같은 점이 보입니다.

- `: string`, `: number`가 **사라졌습니다.** 비유에서 말한 "검수용 메모를 지운다"가 바로 이것입니다.
- 줄 끝에 `;`(세미콜론)이 붙었습니다. JavaScript에서 문장의 끝을 표시하는 기호인데, 생략해도 대부분 괜찮습니다. 컴파일러가 습관적으로 붙여 준 것입니다.
- 실행 결과는 **완전히 같습니다.** 타입은 실행 결과를 바꾸지 않습니다.

::: warning 타입은 실행 중에는 존재하지 않습니다
TypeScript의 타입은 **컴파일 타임에만** 존재하고, JavaScript로 바뀌는 순간 사라집니다. 그래서 "실행 중에 들어온 값이 정말 숫자인지"를 타입이 대신 확인해 주지는 않습니다. 예를 들어 인터넷에서 받아 온 데이터는 따로 검사해야 합니다. 지금은 "타입은 실행 전 검사용"이라고만 기억해 두세요. 이 주제는 Part 4의 [런타임 검증](../part4-async/05-runtime-validation)에서 자세히 다룹니다.
:::

### 8단계: 전체 흐름 한눈에 보기

지금까지의 내용을 순서대로 정리하면 이렇습니다.

```text
[1] 사람이 TypeScript 소스 코드를 씁니다          → hello.ts
        │
        ▼  tsc (TypeScript 컴파일러) : 타입 검사 + 타입 제거
[2] JavaScript 코드가 만들어집니다                 → hello.js
        │
        ▼  런타임 (Node.js 또는 웹 브라우저)
[3] 프로그램이 실행되고 결과가 나옵니다           → 화면에 글자 출력
```

- [1] → [2] 사이가 **컴파일 타임**입니다. 타입 에러는 여기서 잡힙니다.
- [2] → [3] 사이가 **런타임**입니다. 여기서 나는 에러는 프로그램을 실행해야만 알 수 있습니다.

5번 레슨 [첫 프로그램](./05-first-program)에서 이 흐름을 여러분의 PC에서 직접 해 보게 됩니다.

## 자주 하는 실수

### 실수 1: "TypeScript 파일을 웹 브라우저나 Node.js가 바로 실행한다"고 생각하기

```text
잘못된 이해:
hello.ts 를 만들었으니 웹 페이지에 바로 넣으면 실행되겠지?
```

**왜 틀렸나:** 웹 브라우저는 `.ts` 파일을 실행하지 못합니다. 타입 표기(`: string` 같은 것)를 문법 오류로 봅니다.

```text
올바른 이해:
hello.ts  →(tsc로 컴파일)→  hello.js  →  웹 페이지에 hello.js 를 넣습니다
```

::: info 예외도 있습니다
최근 Node.js(22.18 이상, 23.6 이상 등)는 `.ts` 파일의 타입 표기를 **지우기만 하고** 바로 실행하는 기능을 갖추고 있고, `tsx` 같은 도구도 같은 일을 합니다. 하지만 이것들은 **타입 검사를 하지 않습니다.** "타입을 지우고 실행"과 "타입을 검사"는 다른 일이라는 점을 기억하세요. 5번 레슨에서 다시 다룹니다.
:::

### 실수 2: 타입을 붙이면 실행 결과가 달라진다고 생각하기

```ts
// 잘못된 기대: 타입을 number로 붙였으니 글자를 넣어도 자동으로 숫자로 바뀌겠지?
const price: number = Number('4500')
```

**왜 틀렸나:** 타입은 값을 **바꿔 주지 않습니다.** 값이 약속과 맞는지 **검사만** 합니다. 글자 `'4500'`을 숫자로 바꾸고 싶다면 위처럼 `Number(...)`로 직접 바꿔야 합니다. 타입 표기는 "바꾼 결과가 숫자여야 한다"는 약속일 뿐입니다.

```ts
// 올바른 이해: 변환은 코드가 하고, 타입은 결과를 검사합니다
const priceText = '4500'
const price: number = Number(priceText)
console.log(price + 500)
// 출력: 5000
```

### 실수 3: Java와 JavaScript를 같은 언어로 생각하기

```text
잘못된 이해: JavaScript는 Java의 간단한 버전이다.
```

**왜 틀렸나:** 이름이 비슷한 것은 1995년 당시 인기 있던 Java의 이름을 마케팅에 빌려 온 결과일 뿐, 두 언어는 설계도 쓰임새도 다릅니다. "햄"과 "햄스터"만큼 다르다는 농담이 있을 정도입니다.

```text
올바른 이해: Java와 JavaScript는 서로 다른 언어입니다.
TypeScript는 JavaScript에 타입을 더한 언어입니다(Java와는 관계 없음).
```

### 실수 4: "컴파일에 성공했으니 버그가 없다"고 생각하기

```ts
// 타입은 맞지만 계산이 틀린 코드: 할인율 10%를 적용하려고 했습니다
const price: number = 10000
const discounted: number = price * 10 // 0.9 를 곱해야 하는데 10 을 곱했습니다
console.log(discounted)
// 출력: 100000
```

**왜 틀렸나:** TypeScript는 "숫자 자리에 숫자가 있는지"는 검사하지만, **계산의 의도가 맞는지**는 알 수 없습니다. 위 코드는 타입 에러가 없지만 결과는 틀렸습니다.

```ts
// 고친 코드
const price: number = 10000
const discounted: number = price * 0.9
console.log(discounted)
// 출력: 9000
```

타입 검사는 버그를 **줄여 주는** 도구이지, **없애 주는** 도구가 아닙니다. 그래서 Part 6에서는 테스트 작성법도 배웁니다.

### 문제 4 ⭐⭐ 변환 결과 예상하기

다음 TypeScript 코드를 `tsc`로 JavaScript로 바꾸면 어떻게 될지 직접 적어 보세요.

```ts
const menuName: string = '카페라테'
const menuPrice: number = 5000
console.log(menuName, menuPrice)
```

::: details 정답 보기

```js
const menuName = '카페라테';
const menuPrice = 5000;
console.log(menuName, menuPrice);
```
핵심은 `: string`과 `: number`가 사라진다는 것입니다. 세미콜론(`;`)은 있어도 없어도 정답으로 봅니다.
:::

### 문제 5 ⭐⭐ 컴파일 타임 vs 런타임

다음 상황은 컴파일 타임과 런타임 중 언제 알게 되는 문제일까요?

1. TypeScript에서 숫자만 담기로 한 변수에 글자를 넣으려 했다.
2. 인터넷 연결이 끊겨서 서버에서 데이터를 받아 오지 못했다.
3. 사용자가 입력 칸에 나이 대신 "모름"이라고 적었다.

::: details 정답 보기
1. **컴파일 타임** — 코드만 보고도 알 수 있으므로 tsc가 실행 전에 잡아 줍니다.
2. **런타임** — 인터넷이 끊기는 것은 실행해 봐야만 알 수 있습니다.
3. **런타임** — 사용자가 무엇을 입력할지는 실행 중에야 알 수 있습니다. 그래서 이런 값은 코드로 직접 검사해야 합니다.
:::

::: details 정답 보기
예시 답안입니다.

"TypeScript는 JavaScript에 '이 값은 숫자, 이 값은 글자' 같은 **타입**을 적을 수 있게 만든 언어야. 실행하기 전에 타입이 맞는지 검사해서 실수를 미리 잡아 주고, 검사가 끝나면 타입을 지운 평범한 **JavaScript로 변환**해서 실행해. 그래서 JavaScript가 돌아가는 곳이면 어디서든 쓸 수 있어."
:::

## 확인 퀴즈

1. 웹 브라우저 밖에서 JavaScript를 실행할 수 있게 해 주는 프로그램의 이름은 무엇인가요?
2. TypeScript 컴파일러의 명령 이름은 무엇인가요?
3. TypeScript 코드를 JavaScript로 변환하면 타입 표기는 어떻게 되나요?
4. "TypeScript는 JavaScript의 상위 집합이다"는 무슨 뜻인가요?
5. 타입 검사를 통과하면 프로그램에 버그가 없다고 할 수 있나요?

::: details 정답 보기
1. **Node.js**
2. **tsc** (TypeScript Compiler)
3. **사라집니다.** 타입은 컴파일 타임에만 쓰이고, 결과 JavaScript에는 남지 않습니다.
4. 올바른 JavaScript 코드는 거의 그대로 TypeScript 코드이기도 하고, TypeScript는 그 위에 타입 문법을 더했다는 뜻입니다.
5. **아닙니다.** 타입 검사는 "값의 종류가 맞는지"만 확인합니다. 계산 실수나 잘못된 업무 로직은 잡지 못합니다.
:::

## 정리

- **프로그램**은 컴퓨터에게 주는 명령의 모음이고, 사람이 쓴 원본 글을 **소스 코드**라고 합니다.
- **컴파일**은 실행 전에 통째로 번역하는 것이고, **런타임**은 프로그램이 실제로 돌아가는 시간 또는 환경입니다.
- JavaScript는 **웹 브라우저**와 **Node.js**라는 런타임에서 실행됩니다.
- **TypeScript = JavaScript + 타입**입니다. JavaScript의 상위 집합입니다.
- TypeScript는 `tsc`로 타입 검사를 받은 뒤 **타입이 지워진 JavaScript로 변환**되어 실행됩니다.
- 타입은 실행 결과를 바꾸지 않으며, 실행 중에는 존재하지 않습니다.
